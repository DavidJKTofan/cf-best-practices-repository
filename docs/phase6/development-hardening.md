## v1 literal search correction

The original `/api/practices?search=…` accepted up to 200 JavaScript UTF-16 code units but used an escaped `LIKE` pattern. D1's [50-byte pattern limit](https://developers.cloudflare.com/d1/platform/limits/) includes the surrounding `%` and escaping: 49 ASCII characters, 17 three-byte characters or 25 underscores could produce HTTP 500. This was deliberately characterized, not fixed, during the earlier structural phases.

`src/modules/catalog/queries.ts` now uses separately parameterized `instr(lower(column), lower(?)) > 0` predicates, like the existing v2 literal-search approach. It retains:

- The same six fields: title, description, expression, configuration, prerequisites and notes. Fields are not concatenated, so matches cannot span boundaries; nullable fields remain safe.
- SQLite's ASCII-only case folding; non-ASCII case remains exact. This does not introduce Unicode normalization, relevance, stemming or full-text indexing.
- Literal percent, underscore and backslash; query text never becomes SQL syntax.
- Existing NUL removal, trim and 200-code-unit normalization **before** `PublicReads`, with the same effective input consumed by SQL. No extra pattern-byte truncation, cache-key change or narrower acceptance limit.
- AND filters, ordering, v1 record/envelope shape, first-primary reads, cache headers/tags, rate limiting, GET/HEAD/OPTIONS and native-entry exclusion.

No migration, content/seed mutation, write/receipt/hash change, binding or security-policy change is needed. Both old and new substring queries scan candidate text; no indexed-search or performance improvement is claimed. OpenAPI and HTML/Markdown read docs describe the actual bound and case behavior. The isolated Phase 0 proof still demonstrates the underlying D1 `LIKE` limit, but its shared v1 query now correctly returns a successful empty result instead of the historical 500.

New runtime tests failed against the old query (three expected HTTP-500 regressions), then passed after correction, before dependency changes. Coverage includes the original boundary failures, full 200-unit ASCII/multibyte/wildcard-heavy input, positive full-length matches in all six fields, ASCII case, conjunctive filters, negative full-needle checks, short-input parity against the original escaped `LIKE`, NULLs, injection-like strings and shared normalization. The actual built Worker additionally searches a complete 200-character description from the 119-record seed and verifies positive/empty results, HEAD, CORS and cache headers. Fixtures remain disposable.
